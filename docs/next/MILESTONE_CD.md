# SnapIMS Next 0.3.0: pricing and AI workspace preview

Open Settings → Sold pricing, AI workspace or Listing plans. The existing desktop
application is unchanged. Capture/inventory/OCR/backup still work without a server.
The direct Shopify workflow and required physical SIWC acceptance remain incomplete.

## Sold evidence

The native importer reads the actual SnapIMS `pricing_evidence` and
`pricing_evidence_listings` SQLite schema, preserves immutable collection provenance,
and namespaces each dataset by its SHA-256. Identical re-imports add zero rows; a new
source snapshot is a separately versioned evidence dataset. Imports cap 10,000 collections and 16 MB of evidence metadata; export a subset if these limits are exceeded. Imported database bytes
are opened read-only; existing phone evidence is never overwritten.

For a live WAL database, create a consistent export using:

```bash
python integration/snapims/export_pricing.py --source /path/to/pricing_workbench.sqlite3 --output /new/path/phone-pricing.sqlite
```

Transfer that file to the phone and import it in Sold pricing. The database can be
an existing portable dataset; ongoing phone lookups and price review work offline.
SnapIMS does not bundle the owner's real sales database or scrape eBay on Android.

Kotlin ports the source's conservative exact-title/format/seller/sequel/bundle rules
and Decimal HALF_UP statistics. Totals include sold price plus shipping. Average or
median is an explicit operator choice. Only fresh Complete CAD evidence matching the
current normalized title can be applied. No implicit currency conversion, asking-price
substitution, AI-generated price, or overwrite of a manual price. The individual
review requires a separate manual-override checkbox. A batch review handles up to
200 selected records atomically and excludes manual prices. Stale revisions stop
the whole batch. Price provenance records source/collection/hash/method/count/expiry;
a title change or expired evidence invalidates readiness. New-copy vendor/type/weight
defaults are configurable in Settings. Existing values remain unchanged.

Synthetic fixtures are generated by the unmodified desktop pricing functions and
database writer; they are test data only. Real owner evidence and pricing outcomes
have not been tested because no dataset was supplied.

## AI workspace

- Explicit ChatGPT-plan, OpenAI API, Gemini-compatible, Groq, OpenRouter and optional
  on-device OpenAI-compatible endpoint (127.0.0.1:8080/v1) connections. Free tiers and
  `:free` model availability depend on providers. SnapIMS does not run/download a
  local model. No off-device server is mandatory for local inventory operation.
- Dynamic model discovery and a permanent provider/model/authentication binding per
  conversation. No automatic provider/model retry or switch to billed API keys.
- Native CommonMark history, local search, stop, delete and JSON export. HTML remains
  inert; Markdown images do not cause remote fetches. API costs are shown only when
  provider pricing and token usage are supplied; otherwise marked unavailable.
- JPEG/PNG/PDF/text attachments: up to four, 8 MB each; privately copied and SHA-256
  verified. Inline attachments currently require compatible Responses models. No
  Files-upload route is used. Unknown capabilities are gated; optional operator-
  initiated synthetic text/tool/image/file probes can verify them using the selected
  plan or API connection. These probes can consume quota/incur API charges.
- Conversation instructions, local conversation context and streaming. Responses
  success requires `response.completed`; partial/error/cancelled output is retained.
  OpenAI-compatible chat completion success requires [DONE] plus a valid finish reason.
- Local tools are opt-in: matching inventory lookup, exact-title sold evidence, existing recognition results and
  approval status. Enabling them permits matching records to reach the chosen
  provider. Separate opt-in proposals permit metadata corrections, applying confirmed recognition titles or real
  sold evidence and offline listing preparation. The operator reviews exact payloads;
  an item revision plus original-photo fingerprint binds each one-time approval.
  No arbitrary SQL/shell, invented prices, production Shopify writes or messaging.
- The existing offline barcode/Tesseract and API-key recognition paths are retained.
  Chat can read/apply already confirmed current-photo results after approval; it cannot yet invoke a new recognition run or perform Shopify actions. Those
  capabilities remain outside this preview's closed registry.

Requests run while the app process is alive; screen navigation/rotation preserves
jobs, but Android process termination interrupts them. Restart never reissues a
provider request automatically. Backups include evidence, chats and attachments;
restored streaming messages become INTERRUPTED and pending approvals EXPIRED. Keys,
OAuth tokens and installation registration are excluded. A restored device must
reconnect credentials. Conversation exports contain attachment metadata; full bytes
are in the encrypted inventory backup. Chat attachment source files are retained on
the device after conversation deletion; uninstall/clear-data removes private files.

## Listing preparation and unfinished B acceptance

Listing plans are deterministic local DRAFT data with inventory/photo fingerprints,
validation problems and revision. Repeating preparation of unchanged input reuses
its plan. It does not upload media, mutate Shopify or mark an item uploaded. See
SHOPIFY_SETUP.md for the required auth/API review and real development-store gates.
